# Follow-up: StarIntel Wear v0.3.0-alpha, phone-managed installs, and three independent faces

This is the requested detailed follow-up to the brief v0.3.0-alpha release notice. It adds the landed Data Layer installer architecture, queue recovery, independent face packaging, activity views, and goal gauges, with the Quasar release context and exact downloads kept together for setup.

The September 16 release is available as actual APKs, not just a merged branch. The `v0.3.0-alpha` tag resolves to `ab850c313c2572eb68f0608cb7b1338104b4396d`, including the new Quasar phone app, installer recovery, and expanded activity views. This is an alpha release, not a claim of completed physical-device acceptance.

There are three distinct pieces to install: **StarIntel Companion** manages setup and packages on the phone; **StarIntel Wear** runs the watch client and receives package transfers; **Quasar Android** is a separate native phone client. Neon, Command, and Terminal are separate watch-face APKs. They are not Zara Wear, and installing one does not install the others.

## Changes

### Companion manages the watch instead of handing users a pile of APKs

The phone control surface is now StarIntel Companion, with separate Watch Setup, Watch Apps, and Update Manager flows. Setup handles server credentials and configuration. Watch Apps handles the Wear client and the three face packages. Update Manager can select MASTER, LATEST RELEASE, or a specific enumerated version, rather than making every user track build filenames manually.

Packages are described by an update catalog containing package identity, version, size, SHA-256, target device, and installation order. The phone streams the APK to the watch through the Wear Data Layer. When the paired watch is nearby, that path prefers the existing Bluetooth connection. The watch checks the received hash, package name, version, downgrade policy, and signing continuity before asking Android's installer to proceed.

That is a meaningful difference from blind file transfer: receiving bytes is not counted as a successful install, and a filename is not trusted as package identity. Faces install before the Wear client; the receiver's own update goes last so it does not deliberately replace itself halfway through the queue. Android's unknown-source and install confirmations remain part of the process.

There is still a bootstrap boundary. The compatible StarIntel receiver must be installed on the watch once, with matching phone/watch package identity and signing. Data Layer delivery cannot install its own missing receiver. After that bootstrap, normal Companion-managed face installs and updates use the paired-device path instead of requiring a direct ADB session for each package.

Landed package-management work: <https://github.com/lost-rob0t/starintel-wearos/commit/6e7d7612cbaa455995d48495f36cc86c3be3ed0a>

### Install queues expose progress and recover from failure

The installer now shows both per-package and overall progress. It can recover installation status, retry a failed item once, and continue past failures instead of leaving the whole batch stuck behind one package. This makes a mixed result visible: one face failing does not justify claiming that the entire update succeeded, but it also does not have to prevent unrelated packages from being attempted.

The same Companion release adds a phone-app catalog for Quasar. Phone downloads are checked for HTTPS transport, expected length and SHA-256, package identity, downgrade rules, and installed signer continuity before entering Android PackageInstaller. User approval is still required.

Watch installer recovery: <https://github.com/lost-rob0t/starintel-wearos/commit/ffb24addd085feabdd1dedf32d46ac32f0b7e1b8>
Phone package catalog: <https://github.com/lost-rob0t/starintel-wearos/commit/ab850c313c2572eb68f0608cb7b1338104b4396d>

### Neon, Command, and Terminal are now independent watch faces

The old multiplexed arrangement is replaced by three independent Wear OS picker entries: StarIntel Neon, StarIntel Command, and StarIntel Terminal. Each has its own application ID and Watch Face Format layout. Choosing Command no longer means finding a personality switch buried inside the same overloaded face entry.

Their complication geometry is independent too. Neon does not force Command or Terminal to inherit its slot layout. The build and release paths now stage all three APKs, and installation handles removal of the legacy multiplexed face so it cannot obscure the new choices.

Round-screen layout contracts check clipping and overlap against the intended round target. Those checks protect geometry from obvious regressions; they are not a substitute for looking at the rendered face on a physical Galaxy Watch. This update does not claim that a screenshot or real-device visual acceptance was completed during publication.

Separate-face implementation: <https://github.com/lost-rob0t/starintel-wearos/commit/d3c03f840e19c2ce9a08a229f4e0386f7864bd84>

### Activity is easier to inspect, and gauges use real values

The activity view now has line graphs for 1 minute, 5 minutes, 15 minutes, 1 hour, 6 hours, 1 day, and 1 week, with automatic range rotation and per-document-type views. Stackable graph complications and a Stack tile give the same activity information additional watch surfaces. Explorer can surface random documents, and Explorer/Search provide paths into graph views. The watch presentation also received pure-black styling work.

These activity plots describe observed corpus activity. They should not be confused with a document relationship graph merely because both are graphs. A plot over time and a view of linked documents answer different questions.

The merged goal-gauge work also provides on-watch configuration for total documents, targets, a chosen document type, and an hourly document-rate goal. Ranged complications consume provider values and ranges rather than drawing a decorative bar at a fixed percentage. System metrics such as battery remain supplied by their actual complication provider.

Activity views and watch UX: <https://github.com/lost-rob0t/starintel-wearos/commit/ffb24addd085feabdd1dedf32d46ac32f0b7e1b8>
Goal gauges: <https://github.com/lost-rob0t/starintel-wearos/commit/3282304db492bebb629c7f9da8a4c8f9dfb34b60>

### Quasar now has a separate native Android package

Quasar Android is included in this release as an independently installable phone app using the current Star server API. Authentication supports username/password login and a direct API key. A newly minted or supplied bearer credential is checked against the server's authentication context before it replaces the credential protected by Android Keystore.

Passwords are not persisted, and credentials are not placed in update manifests or logs. The separation is deliberate: Companion manages packages and watch configuration; Quasar is the native phone client. Installing Quasar does not make it a watch face, and installing a watch face does not configure a server connection.

Native Quasar and authentication: <https://github.com/lost-rob0t/starintel-wearos/commit/ab850c313c2572eb68f0608cb7b1338104b4396d>

## Which APK goes where?

On the **phone**, install StarIntel Companion. Install Quasar Android as well to use the separate native client. On the **watch**, install StarIntel Wear for the client and package receiver. Neon, Command, and Terminal also belong on the watch; install the faces you intend to select.

For a fresh setup, bootstrap the Wear receiver, complete Companion pairing/configuration, then use Watch Apps and Update Manager for the desired packages. Read the result for each installation rather than assuming that reaching the end of a batch means every package succeeded. A successful build or release upload alone does not prove that a particular phone/watch pairing has passed hardware acceptance.
