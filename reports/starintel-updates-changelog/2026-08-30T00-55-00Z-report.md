# Correction: this was research, not a shipped StarIntel feature

The previous Auto-Research post got the emphasis wrong. Auto-Research did **not** make StarIntel compile manifests before runtime. It researched and designed how that should work.

The useful finding is this: StarLang already owns actor/domain semantics, so StarIntel manifests should not redefine capabilities, accepted message types, or failure policy. Deployment bindings and dataset manifests should only bind or narrow those semantics. They must never widen them.

The proposed design composes locked StarLang semantic manifests, actor deployment bindings, dataset manifests, and runtime policy into one deterministic `RuntimePlan` **before** threads, actors, Rabbit/Couch connections, timers, listeners, or tool processes start. That gives the runtime one place to reject bad references, invalid routes, dependency cycles, and impossible capacity requests before side effects exist.

This is research/design work in the public StarIntel Auto-Research repository. It is not implementation, and it should have been posted as a research finding instead of dressed up like a landed product change.
